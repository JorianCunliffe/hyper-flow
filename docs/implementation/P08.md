# Phase 08 — Diary coordination

Status: implementation released and local checks passed; live calendar provider acceptance remains pending. Google is the first provider because the authenticated settings page showed the CEO's existing Workspace connection. That connection's document scopes do not imply calendar access. Calendar OAuth read/write consent and a selected calendar policy remain required for live provider acceptance. No calendar was booked and no invitation was sent by this implementation session.

HyperFlow owns calendar credentials through its existing encrypted Workspace credential store, per-project calendar policies, proposals, version-specific Asks, operation claims and provider receipts. Communications owns normalized calendar event context and exact participant enrichment. The existing memory stays in Communications; no separate memory service is introduced.

## Implemented scope

- Diary UI and `/api/calendar`: connected calendar discovery; explicit work hours, IANA timezone and buffers; booking disabled by default; administrator configuration; 14-day UI view and bounded 31-day API windows.
- Create, update and cancel proposals for personal timed events. Recurrences are expanded for availability and the UI can explicitly change or cancel one occurrence. Guest invitations, whole-series mutations and all-day mutations are unavailable in this initial provider scope. Calendar read access may observe those events without booking them.
- Separate approval of exact normalized details and policy revision, pinned policy snapshot, designated reviewer and current membership checks. Provider revisions are checked before execution and update/delete use `If-Match`. Changes after approval hold the proposal; a new proposal is required.
- Server-only calendar ledger and one active operation per tenant/calendar connection. Recheck provider availability immediately before writing and again afterward. Stable provider event IDs and operation markers reconcile lost responses without a repeated write. Uncertain outcomes hold subsequent operations until reconciled. Disabling booking is allowed during an active operation and is rechecked before dispatch; it cannot recall an already accepted provider write.
- Calendar read and booking OAuth scopes are explicitly selected, with no change to existing document-only connection requests. Personal creation has no attendees and disables default reminders. `sendUpdates=none` is additional provider configuration, not treated as proof that guest updates are safe.
- Read-only event observations can be explicitly shared with a project. Participants are normalized/enriched in Communications. A preparation flow reads current permitted context and accepted obligations before drafting a briefing; it requires its own approval. Calendar observations do not create or fulfill operational promises.
- Communications migration 023 preserves observation order and participant snapshots atomically, checks tenant ownership of linked references, and excludes cancelled events from automatic candidate matching. Failed context sync remains visible separately from a verified booking and can be retried without booking again.

## Local checks and limits

Unit tests cover approval/version gates, wrong reviewers, draft-only invitation restrictions, tenant isolation, stable reconciliation after an accepted write loses its response, concurrent bookings, changed revisions, disabled booking, cancellation, preserved provider properties, explicit recurring-occurrence selection and daylight-saving gaps/ambiguities. Real Firebase + Communications HTTP/PGlite integration proves cold operation claims, one write under contention, server-only ledger rules and canonical observation persistence. Google HTTP behavior is simulated in these tests; they do not prove live Google authorization or delivery.

The local browser fixture verified a 10–11 am Brisbane proposal, open Ask, disabled booking policy and no browser errors. The provider lacks atomic availability-and-insert; HyperFlow serializes its own operations and checks afterward, but an independently edited calendar can race a write. Such conflicts require review; the system does not silently delete a created event. All-day overlaps are conservatively held. The wall-time UI rejects repeated daylight-saving hours; the API accepts explicit-offset instants. Event lists fail closed at 2,500 entries. Ledgers are bounded to 200 proposals and 4 MB, with at most 100 calendar ledgers returned. Calendar context currently associates an event with the explicitly selected project; it is not a grant to all projects or contacts.

Live acceptance remains pending: calendar-specific OAuth consent, selected calendar/work-hours/buffer/booking policy, a controlled create-update-cancel round trip, and provider/context reconciliation. Whole-series and guest-invitation writes are deliberately outside this initial scope and are not claimed implemented.

Event-list expansion is used for availability so the selected occurrence can be excluded during an update.
