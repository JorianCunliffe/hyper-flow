# Phase 06 — Visible, reusable flows

Status: released and controlled live acceptance verified, 9 September 2026 (Australia/Brisbane). Entry baseline is the verified Phase 05 release, recorded in P05.md. The active programme goal continues through Phase 12.

Implement a bounded action catalog and request compiler; preserve typed inputs, missing-input Asks and explicit version approval. Use the existing HyperFlow flow engine and action executors. Communications remains the channel/context authority. Unsupported calendar, publishing and artifact capabilities cannot be invented by the compiler.

Store immutable template versions and server-owned run snapshots in HyperFlow. Keep each run tied to an accessible existing project. A reviewed template edit creates a new version; existing runs retain their pinned version. Claims and stable step operation identities must be persisted before dispatch. Pause/cancel prevent new steps and preserve receipts for effects already accepted by a provider. An uncertain operation requires reconciliation before any new attempt.

UI and REST must expose proposed steps, editable inputs, owners, dependencies, sources, approval/waiting reasons, execution status and receipts. A successful reviewed run can be promoted to a reusable template; reuse still requires current authority and version approval. Provider callbacks must resolve the exact persisted run/step, including after browser closure.

Acceptance includes unsupported tools, malformed graphs/cycles, missing inputs, changed approvals, tenant/project denial, concurrent/repeated execution, restart after dispatch, stale callbacks, pause/cancel, template version isolation and a controlled live journey. Local failure cases and the production journey are distinguished below.

## Implemented contract

`GET /api/flows` lists the latest 100 server-owned flow records; `GET /api/flows?id=...` retrieves an accessible record. Authenticated membership determines tenant and project scope. `POST /api/flows` supports `compile`, `create`, `revise`, `approve`, `reject`, `start`, `advance`, `pause`, `resume`, `cancel`, `reconcile`, `review`, `promote`, and `migrate`. Mutations carry `id`, `expectedRevision`, and the relevant version/hash/run identity. Start additionally requires a stable `runKey`; replay returns the original run, including after a lost response. These routes reuse the existing Gemini hosting function, keeping the twelve-function limit.

The seven-entry catalog covers project communication evidence, mailbox drafts, SMS, outbound calls, report drafts, and granted Google document/sheet reads. Inputs are bounded strings; recipients use validated email/international phone formats. Unknown actions, fields, dependencies and cycles are rejected. Missing inputs create an existing-model Human Ask; supplying them creates a separate version with a separate approval Ask. No model output supplies authority. Current tenant channel policy, mailbox permission and resource grants still apply at execution.

The existing `advanceFlow` engine determines readiness and `applyActionRun` records outcomes. Immutable plan snapshots live under the server-only `visible_flows` root, outside the browser-writable projects tree. Each operation is claimed transactionally before dispatch. Matching callbacks continue these runs through the existing authenticated Communications event path. Channel transport errors/deadlines remain uncertain, not permission to repeat an effect. SMS/voice reconciliation reads an exact tenant/project/run/step/channel receipt from Communications; it does not dispatch. Draft uncertainty remains held for mailbox reconciliation. New attempts are not created automatically.

Version history is capped at 100 versions and 100 runs per definition, 100 KB per proposal and 4 MB total per record. Phase 11 will add broader paginated operations/export tooling. Migration is explicit and only permitted for a paused run with no dispatched step; a partially executed run must retain its version or be replaced by a separately approved new run. Pause/cancel cannot recall provider effects already claimed or accepted. Run control history records the acting member. Report completion means saved draft text, not verified facts, an exported artifact, delivery, or fulfilled obligations.

Communications owns evidence filtering/freshness. A permitted response can contain safe raw evidence while indicating withheld stale or out-of-scope material. The run preserves that indication; a downstream report receives a deterministic visible incompleteness notice. It never receives withheld material. No new memory layer or Communications deployment is required for this phase.
