## Design and acceptance plan

- HyperFlow stores versioned operational obligations, accepted terms, evidence references, submissions and an append-only decision history. Communications extracted rows remain evidence, including their legacy statuses.
- Reuse HumanAsk, createAsk, response validation and response recording for human gates. Commitment reviews affect only their own aggregate; they never manufacture workflow runs or release unrelated flow gates.
- Per-obligation atomic transactions enforce expected versions and current Ask identity. Source-derived candidate IDs are stable; refresh cannot silently accept terms or fulfill an obligation.
- Require explicit owner, beneficiary, deliverable, acceptance criteria, due instant/timezone and acceptance evidence. Unknown terms create clarification Asks. Proposed terms retain the previous accepted contract until approved.
- Expose review, progress, renegotiation, submission, revision, fulfillment, dispute and cancellation through authenticated REST and a readable UI with owed/owing, contact/project filters and evidence drill-down.
- Follow-up rules are saved proposals/settings only; no scheduler dispatch in this phase.
- Verify lifecycle, duplicates/concurrency, stale or unauthorized replies, tenant/project isolation, source refresh, timezone handling and draft-versus-fulfilled distinction; run integration and browser checks before completing the implementation gate.
